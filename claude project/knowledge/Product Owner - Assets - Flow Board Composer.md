# Product Owner Flow Board Composer

The code that composes a checked Flow model into a framed FigJam board, and how to fill its model by hand. A Project has no script to fill it, so the model is written here as JSON and placed into the code before the `use_figma` call.

---

## 1. HOW TO USE IT

1. Check the Mermaid model against Templates - Flow Mode Section 5 and the chosen Flow Type, exactly as for any write
2. Write the MODEL as one JSON object, following Section 2 for its type. Every value comes from the checked model, never from memory of the sources
3. Copy the code in Section 4 whole, from its first line to its last. Replace the one `__MODEL__` in its first line with that JSON and the one `__THEME__` right after it with the `THEME` line in Assets - Flow Board Design, `{}` for the shipped design. Change nothing else, because one dropped line breaks the board and the call cannot tell you which. The code came back whole only when all three hold: it runs 155 lines and 47,390 characters, its first line starts `const MODEL=__MODEL__;const THEME=__THEME__;` and its last line ends `createdCount:created.length};`. If any one fails, it did not come back whole
4. Send the result as the `code` of one `use_figma` call, one diagram per call, after the gate's yes. The whole call must stay under 50,000 characters. The code takes 47,372 of them before its two placeholders are filled, so the model JSON, written compact with no space after a comma or a colon, and the `THEME` line together must stay under 2,628 characters. The shipped `{}` costs 2, and the largest shipped example model, Examples - Flow - Process Commission, runs 2,610. A diagram that will not fit is split, never trimmed
5. Read the return value. It holds `boardId`, `tag`, `counts` beside `expect`, the `elements` and `links` it drew with their ids, `warnings` and a screenshot of the board. Counts that differ from `expect`, or any warning, are a finding reported as measured. A thrown error that starts `nothing was drawn` means two zones would have overlapped and nothing was written to the board. Do not retry the same model and do not read the board. Split or regroup the zones in the model, check it again against Templates - Flow Mode Section 5 and fill the code again. Say in the reply that the first compose drew nothing
6. Read the board back with `get_figjam` on `boardId`, as Templates - Flow Mode Section 7 sets out

When the code in Section 4 does not come back whole from this Knowledge file, do not rebuild or shorten it. Write the board through Figma's `generate_diagram` instead, as Templates - Flow Mode Section 6 sets out for the generated route, and say in the reply that the board was generated rather than composed.

## 2. THE MODEL

Every model carries `title`, `subtitle` and `source` strings, from the `%% title:`, `%% subtitle:` and `%% source:` lines, empty when a line is absent, and `expect`, the counts the read-back looks for: `{"nodes": <n>, "connectors": <n>}`. A `%% focus: <id> because <reason>` line adds `"why"`, the reason in 30 characters at most, which the key draws as `In focus: <reason>`. On a user flow or a process that line names the node its `style` line marks. A `%% notes: <id>, <id>` line, written when a single sticky will sit beside those nodes, adds `"gap":368`, which moves the key down by one sticky and its gap so a node on the bottom row keeps the side below it free.

### Graph types: user flow, process, architecture, state and ER

```text
{"type": "graph", "profile": "user-flow" | "process" | "architecture" | "state" | "er",
 "direction": "LR" | "TB", "zoneMode": "stage" | "lane" | "group",
 "zones": [{"id", "label"}], "nodes": [{"id", "label", "kind", "zone"}],
 "edges": [{"from", "to", "label"}], "edgeStyles": [...], "expect": {...}, "title", "subtitle", "source"}
```

- `direction` is `TB` for a `TD` or `TB` header and `LR` otherwise. A state diagram takes the direction its `direction` line names and `TB` when it has none. An ER diagram takes the direction its `direction` line names and `LR` when it has none
- `zoneMode` is `lane` for a process with lanes, `group` for a state or ER diagram and `stage` for everything else
- `zones` lists the `%% zone:` lines in the order written, each `id` the label in lower case with every run of other characters as one hyphen and no hyphen at either end. A process takes its lanes in declared order instead, and an architecture its lanes in the order client, gateway, service, async, datastore, external, each `label` the lane's label. A state diagram's zones are its composites
- Each node's `zone` is the zone id it sits in, or `null`
- A step a `%% detail: <id> | <line> | <line>` line gives a body carries `"body": ["<line>", ...]`, its lines in order. The code sets the label in Bold over an empty line and the body at body size
- A node the model plans the accent on carries `"accent": true`, as the kind table below says, and no other node does
- An edge carries `"style": "status"` for a `-.->` into a status, `"style": "dashed"` for any other `-.->` or `..` line, `"twoWay": true` for `<-->` and `"ends"` for every ER relationship, as the kind table below sets out. An empty label is `""`
- An architecture edge written `a <---|label| b` enters the model as the edge from `b` to `a`
- `edgeStyles` names each line style the board uses once, for the key: `solid` for a plain one-way edge on a user flow, process, architecture or state diagram, `dashedOptional` for a dashed edge on a user flow or process, `statusMove` for a status move, `dashedAsync` for one on an architecture, `twoWay`, and on an ER diagram `identifying` and `nonIdentifying`
- `expect.nodes` counts `nodes` and `expect.connectors` counts `edges`

A node's `kind` follows its shape and place:

| Type | Kind |
|---|---|
| User flow, process | A rhombus is `decision`, a circle `merge`, a cylinder `datastore`, a subroutine `subprocess` and a parallelogram `io`. A stadium no edge enters is `start`. A stadium no edge leaves is `success` when a `%% goal:` line names it and its `style` is not the light red pair, `error` when its `style` takes the light red pair, `success` when it takes any other pair, and when unstyled `success` if no end is the goal yet and it is the end the longest path reaches, otherwise `exit`. Any other styled step is `focus`, and every styled node, an end, a decision and a start included, keeps the kind its shape gives it and also carries `"accent": true`. A plain node in the lane a `%% status:` line names is `status`, drawn as a chevron. Everything else is `screen` on a user flow and `step` on a process |
| Architecture | The lane sets it: `client`, `gateway`, `service`, `datastore`, `external`, and `queue` for the `async` lane. A `%% focus: <id>` line puts `"accent": true` on that node |
| State | Each `[*]` arrow gets its own node: `"__start_<n>"` with label `"[start]"` and kind `initial` where an arrow leaves `[*]`, `"__end_<n>"` with label `"[end]"` and kind `final` where one enters it, numbered in the order they appear and zoned in the composite they sit in. A `<<choice>>` state is `choice` and a `<<fork>>` or `<<join>>` is `fork`. A state entered from a top-level start is `firstState`, one that leaves to a top-level end is `finalState`, and every other state is `state`. A composite is a zone, never a node, and an edge to or from it names the composite's id. A `%% focus: <id>` line puts `"accent": true` on that state |
| ER | Every entity is `entity`, its `label` the alias or the id, with `"fields": [{"type", "name", "keys"}]` where `keys` is the entity's `PK`, `FK` and `UK` marks joined by `, `, or `""`. A relationship runs from the left entity to the right, labelled `<label> (<left> to <right>)`, with each end in words: `\|\|` is `1`, `\|o` or `o\|` is `0..1`, `}o` or `o{` is `0..n` and `}\|` or `\|{` is `1..n`. Its `"ends"` gives the mark each end draws, one character for the left end and one for the right: `1` for `\|\|`, `?` for `\|o` or `o\|`, `*` for `}o` or `o{` and `+` for `}\|` or `\|{`, so `\|\|--o{` is `"1*"`. A `%% focus: <id>` line puts `"accent": true` on that entity |

### Sequence

```text
{"type": "sequence", "participants": [{"id", "label"}], "messages": [{"from", "to", "arrow", "label"}],
 "expect": {"nodes": <participants>, "connectors": <messages>}, "title", "subtitle", "source"}
```

Participants come in declared order, then any others in the order a message first names them, each `label` its id. `arrow` is `request` for `->>`, `reply` for `-->>`, `async` for `-)` and `asyncReply` for `--)`. A `%% focus: <number>` line puts `"accent": true` on that message, counted from 1 in the order written. The `title` is the diagram's `title` line when it has no `%% title:`.

### Gantt

```text
{"type": "gantt", "unit": "day" | "minute", "origin": "YYYY-MM-DD" | "HH:mm", "span": <number>,
 "sections": [{"label", "tasks": [{"id", "name", "tags", "start", "end", "after"}]}], "edgeStyles": [...],
 "expect": {"nodes": <tasks>, "connectors": <after ids>}, "title", "subtitle", "source"}
```

`unit` is `day` for `dateFormat YYYY-MM-DD` and `minute` for `HH:mm`. `origin` is the earliest task start. Each task's `start` and `end` are its offsets from the origin in that unit, an `after` task starting where the latest task it names ends and a task with neither starting where the task above it ends. A milestone's `end` equals its `start`. A task written `after` carries `"after"`, the list of ids it names, and the code draws one arrow from each of those bars to it, so `expect.connectors` counts every id in every `after`. A task with no `after` leaves the key out. `edgeStyles` is `["solid"]` when any task carries `after`, so the board's key names its arrows `Leads to`, and `[]` otherwise. `span` is the largest `end`. `tags` lists the task's `done`, `active`, `crit` and `milestone` tags, `id` is `""` when the task has none, and a task outside any section sits in a section labelled `Tasks`. A `%% focus: <id or name>` line puts `"accent": true` on that task.
