# v1.16.0.0, Templates Match the Operator's Writing

The templates now match how the operator writes in ClickUp. Story and Epic openings sit at H4. Expected outcomes is a bold label inside Solution. About is H2 in every template. Story requirements are checklist items and every checkbox in an artifact is written `[]` with no space.

Under `## Requirements` a checkbox item passes and a plain `*   ` bullet blocks. A new rule blocks a `[ ]` checkbox in a Product Owner deliverable. How ClickUp renders `- []` is unverified. The operator chose `[]` knowing this.

## Why This Release

The operator's newest hand-written exports already used these forms. The templates still taught the old ones. The rules banned a checkbox inside a Story's Requirements. The format gate blocked one. A Story written the operator's way failed the gate.

## What's New at a Glance

- **A Story opens in the operator's form.** A Story opens with `## About`, then `#### Problem` and `#### Solution`. Solution closes on a bold `**Expected outcomes**` label with a `* * *` divider under it, never a heading.
- **An Epic uses the same depth.** An Epic's Problem, Goal and Solution sit at H4 too and the spacers between them are `####   `.
- **Task and Bug templates write About at H2.** They write `## About` at H2 and keep their other sections at H3.
- **A Story requirement is a checkbox item.** It is a `- []` item under its bold group name. Items stay hard constraints and never build steps, and a `**Checklist**` label is still banned.
- **Every artifact checkbox is written `[]`.** Mark-as-done lines, Ready and Done gates, Task and Bug checklists and `*   []` in a Doc all use that form. The model's own quality checklists inside the references keep `- [ ]`, since they are never output.
- **"Build checklist" now reads "build steps".** The new wording appears wherever the old phrase meant implementation steps in Requirements, so the new checkbox marker is not read as banned.
- **The validators see both checkbox forms.** Both format validators, the shared one and this system's own copy, read `[]` and `[ ]` as checkboxes, so every rule that used to miss `[]` still fires.
- **A checkbox requirement now passes.** Under `## Requirements` a plain `*   ` bullet blocks and a checkbox item passes.
- **A spaced checkbox fails in this system.** A new rule blocks a `[ ]` checkbox in a Product Owner deliverable, keyed per system so other systems and the sources are untouched.
- **ClickUp's rendering of `- []` is unverified.** Standard markdown renders only `- [ ]` as a checkbox. Every ClickUp note in this repo was checked with that form and the operator chose `[]` knowing this.
- **The files you open move version.** `SKILL.md` moves from 1.15.0 to 1.16.0, `description.json` moves to 1.16.0.0 and the kernel moves from v1.18.0 to v1.19.0 with the operator's review pending. Template, mode and playbook versions move, each mirror is renamed and every live reference is repointed.

## Template Openings

#### Stories Open as the Operator Writes

A Story opens with `## About`, then `#### Problem` and `#### Solution`. Solution closes on a bold `**Expected outcomes**` label with a `* * *` divider under it, never a heading. That is the opening the operator already writes in ClickUp, and it is the opening the templates now teach.

&nbsp;

#### Epics Use the Same Heading Depth

An Epic's Problem, Goal and Solution sit at H4 too. The spacers between them are `####   `. The Epic opening now uses the same depth as the Story opening.

&nbsp;

#### Task and Bug Write About at H2

Task and Bug templates write `## About` at H2 and keep their other sections at H3. About is H2 in every template.

---

## Requirements and Checkboxes

#### Requirements Are Checkbox Items

A Story requirement is a `- []` item under its bold group name. Items stay hard constraints and never build steps. A `**Checklist**` label is still banned.

The rules banned a checkbox inside a Story's Requirements and the format gate blocked one. A Story written the operator's way failed that gate. A checkbox item is now the requirement form.

&nbsp;

#### Artifact Checkboxes Drop the Space

Every checkbox in an artifact is written `[]`, with no space inside the brackets. That covers Mark-as-done lines, Ready and Done gates, Task and Bug checklists and `*   []` in a Doc. The model's own quality checklists inside the references keep `- [ ]`, since they are never output.

&nbsp;

#### Build Steps Replace Build Checklist

"Build checklist" now reads "build steps" wherever it meant implementation steps in Requirements. The new checkbox marker is not read as banned.

&nbsp;

#### ClickUp Rendering Stays Unverified

Standard markdown renders only `- [ ]` as a checkbox. Every ClickUp note in this repo was checked with that form. How ClickUp renders `- []` is unverified. The operator chose `[]` knowing this.

---

## The Format Gate

#### Validators Read Both Checkbox Forms

Both format validators, the shared one and this system's own copy, read `[]` and `[ ]` as checkboxes. Every rule that used to miss `[]` still fires.

&nbsp;

#### Checkbox Items Now Pass the Gate

Under `## Requirements` a plain `*   ` bullet now blocks and a checkbox item passes. The rules banned a checkbox inside a Story's Requirements and the format gate blocked one, so a Story written the operator's way failed the gate.

&nbsp;

#### This System Blocks the Spaced Form

A new rule blocks a `[ ]` checkbox in a Product Owner deliverable. The rule is keyed per system, so other systems and the sources are untouched.
