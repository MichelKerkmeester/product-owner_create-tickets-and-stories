# BE - TRACK - Carrier tracking webhook

## About

---

Carrier tracking events reach shipping-service by webhook, one for each scan of a parcel. They can arrive out of order, and the carrier retries any event that is not acknowledged. This task receives, checks, stores and maps those events, so the timeline and the delivery estimate on every surface carry the parcel's current state.

How a mapped event reaches the order status is open in the Story. The status handoff to orders-service waits for that decision. The three front-end tasks depend on this task's data.

### Requirements

---

1.  **Receiving**

---

The carrier's events are received as one event type, in their own subscription.

**Checklist**

- [] The endpoint is `/webhooks/carrier/tracking` on shipping-service
- [] Each event has the type `tracking.updated`
- [] Tracking events keep their own subscription and secret, separate from the label webhooks
- [] The endpoint returns a 2xx within `5 seconds`, since any other answer counts as a failed delivery

2.  **Signature**

---

**Checklist**

- [] Each request is checked against `X-Carrier-Signature`, the hex HMAC-SHA256 of the raw body keyed with the tracking subscription's own secret

3.  **Duplicates and retries**

---

**Checklist**

- [] Each event is deduplicated on `event_id`, which is the same on every retry
- [] After a failed delivery the carrier makes up to `5 attempts`, waiting `1 min`, `5 min`, `15 min`, `1 h` and `6 h` before each, then drops the event
- [] A dropped event cannot be recovered, since `GET /v1/shipments/{shipment_id}` returns label fields only and tracking history is not part of Fernhouse's plan with the carrier

4.  **Stored fields**

---

**Checklist**

- [] Each event stores `event_id`, `shipment_id`, `tracking_number`, `status_code`, `occurred_at`, `sent_at`, `eta_window` and `location`

5.  **Status codes**

---

**Checklist**

- [] `PU` arrives once per parcel at the `18:00` collection
- [] `IT` arrives once per hub scan, usually `2 to 4` per parcel and more for the UK
- [] `OD` always carries `eta_window` and can arrive again after `EX`
- [] `DL` carries `delivered_to` as `recipient`, `neighbour` or `parcel_point`
- [] `EX` carries `exception_code` as `NOT_HOME`, `ADDRESS_PROBLEM`, `DAMAGED` or `REFUSED`
- [] After `EX` with `NOT_HOME` the carrier tries again the next working day, which sends a new `OD`

6.  **Order and window**

---

**Checklist**

- [] Events are ordered by `occurred_at`, never by arrival
- [] An event with an `occurred_at` older than the newest event held for its parcel is stored in the history and does not change the status shown
- [] The newest `eta_window` by `occurred_at` is the window shown

7.  **Volume**

---

**Checklist**

- [] About `3,100` parcels leave on a normal working day, and up to `5,400` on the busiest days
- [] Each parcel produces `5 to 8` events, so the endpoint takes up to about `43,000` events on a peak day
