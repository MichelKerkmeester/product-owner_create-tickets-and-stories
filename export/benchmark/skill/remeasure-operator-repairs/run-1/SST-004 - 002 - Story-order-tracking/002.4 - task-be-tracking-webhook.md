# BE - TRACK - Tracking webhook

### About

---

shipping-service receives the parcel carrier's tracking events, stores them and maps each carrier code to a status the customer sees. This gives the order page on web, iOS and Android a status per parcel that moves as the parcel moves.

A dropped event is gone for good. `GET /v1/shipments/{shipment_id}` returns label fields only, and tracking history is not part of our plan with the carrier. A missed `DL` would leave the parcel on its last status, so every event has to be accepted in time.

The source for the carrier facts below is Yusuf's write-up of the carrier's tracking events guide, version 2.4, and the carrier call on 2026-09-19.

### Requirements

---

### **Receiving events**

---

1.  **Webhook endpoint**

---

The carrier posts one event type, `tracking.updated`, for every scan of a parcel. Delivery follows the same rules as the label webhooks.

**Checklist**

- [ ] `tracking.updated` events are received at `/webhooks/carrier/tracking` on shipping-service
- [ ] The tracking path stays separate from the label event path, because the carrier signs each subscription with its own secret
- [ ] Every event is checked against `X-Carrier-Signature`, the hex HMAC-SHA256 of the raw body keyed with the tracking subscription's own secret
- [ ] An event whose signature does not match is not stored
- [ ] A 2xx goes back within `5 seconds`, because the carrier counts anything else as a failed delivery
- [ ] Events are deduplicated on `event_id`, which stays the same on every retry, because delivery is at least once

**User Story**

- **Given:** the carrier sends a scan for a parcel
- **When:** the event reaches shipping-service with a valid signature
- **Then:** it is stored once and acknowledged within `5 seconds`

---

2.  **Retries and volume**

---

After a failed delivery the carrier makes up to `5 attempts` more, waiting `1 min, 5 min, 15 min, 1 h, 6 h` before each one, then drops the event.

**Checklist**

- [ ] The endpoint handles about `3,100` parcels on a normal working day and up to `5,400` on the busiest days so far this year
- [ ] At `5 to 8` events per parcel, a peak day of up to about `43,000` events is accepted within the `5 seconds` limit

---

### **Statuses**

---

3.  **Status mapping**

---

**Checklist**

- [ ] `PU` and `IT` map to `Shipped`
- [ ] `OD` maps to `Out for delivery`
- [ ] `DL` maps to `Delivered`, whatever its `delivered_to` value: `recipient`, `neighbour` or `parcel_point`
- [ ] `EX` maps to `Delivery failed`, whatever its `exception_code`: `NOT_HOME`, `ADDRESS_PROBLEM`, `DAMAGED` or `REFUSED`
- [ ] A new `OD` after an `EX` moves the parcel back to `Out for delivery`
- [ ] Each parcel's statuses, the date and time of each step and its newest delivery window are available to the order page on web, iOS and Android

---

4.  **Event order**

---

Events can arrive out of order. Hub scans upload in batches, so an `IT` can arrive after the `OD` for the same parcel, on busy days by more than an hour, and retried events arrive late by design.

**Checklist**

- [ ] Events are ordered by `occurred_at`, never by arrival
- [ ] An event whose `occurred_at` is older than the newest one held for that parcel is stored for the history and does not change the status shown
- [ ] The newest `eta_window` by `occurred_at` wins
- [ ] A parcel with no `eta_window` gets no estimate. `OD` always carries one, and `IT` carries one only when the carrier can predict the day, mostly inside the Netherlands and Belgium

**User Story**

- **Given:** a parcel's newest stored event is an `OD`
- **When:** an older `IT` for the same parcel arrives
- **Then:** the `IT` is stored for the history and the parcel stays `Out for delivery`

---

### **Retention**

---

5.  **Tracking history**

---

**Checklist**

- [ ] Tracking events are kept for `90 days` after delivery
- [ ] After those `90 days` the last status stays available to the order page
