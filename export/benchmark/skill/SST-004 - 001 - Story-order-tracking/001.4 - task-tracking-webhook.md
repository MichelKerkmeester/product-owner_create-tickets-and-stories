# BE - TRACK - Tracking webhook and status mapping

### About

---

Receive the parcel carrier's `tracking.updated` events, store them per parcel and map each carrier code to the status the customer sees on the order page. The web, iOS and Android timelines read the carrier statuses from this, so the order page stops ending at `Shipped`. `Packed` is out of this task, because orders-service already receives it from the warehouse system.

A dropped event cannot be fetched from the carrier again, because `GET /v1/shipments/{shipment_id}` returns label fields only and tracking history is not part of the carrier plan. A missed `DL` would leave the order on its last status, so every delivery the carrier makes has to be accepted and kept.

### Requirements

---

1.  **Receive tracking events**

---

The carrier sends one event type, `tracking.updated`, for every scan of a parcel. It follows the same delivery rules as the label webhooks, and its path stays separate from the label path because each subscription is signed with its own secret.

**Checklist**

- [ ] Events arrive at `/webhooks/carrier/tracking` on shipping-service
- [ ] Each request is verified against `X-Carrier-Signature`, the hex HMAC-SHA256 of the raw body, keyed with the tracking subscription's own secret
- [ ] A 2xx goes back within `5 seconds`, since anything else counts as a failed delivery and starts the retry schedule of up to `5 attempts` at `1 min, 5 min, 15 min, 1 h, 6 h`
- [ ] Events are deduplicated on `event_id`, which stays the same on every retry
- [ ] Each event is stored with its `event_id`, `shipment_id`, `tracking_number`, `status_code`, `occurred_at`, `sent_at`, `eta_window` and `location`
- [ ] Intake holds up to about `43,000` events on a peak day, from up to `5,400` parcels at `5 to 8` events each

---

2.  **Map carrier codes to customer statuses**

---

The order page shows Fernhouse statuses, never carrier codes, and `Delivery failed` carries no reason in this story.

**Checklist**

- [ ] `PU` and `IT` map to `Shipped`
- [ ] `OD` maps to `Out for delivery`
- [ ] `DL` maps to `Delivered`
- [ ] `EX` maps to `Delivery failed`, and no `exception_code` reaches the order page
- [ ] A new `OD` after an `EX` moves the parcel back to `Out for delivery`

---

3.  **Order by scan time**

---

Events arrive out of order. Hub scans upload in batches, so an `IT` can land after the `OD` for the same parcel, on busy days by more than an hour, and retries arrive late by design.

**Checklist**

- [ ] Events are ordered by `occurred_at`, never by arrival
- [ ] An event whose `occurred_at` is older than the newest one held for that parcel is stored for the history and does not change the status shown
- [ ] The current `eta_window` is the newest one by `occurred_at`
- [ ] A parcel with no `eta_window` on any event has no estimate, and none is derived from the dispatch date

---

4.  **Keep tracking for 90 days after delivery**

---

**Checklist**

- [ ] Tracking events are kept for `90 days` after delivery
- [ ] After that the order page receives the last status only
