# Iteration 002 — Ordering a screenshot set, and telling a screen from a state

## Focus

Iteration 2 takes the two questions iteration 1 left open. First, ordering: what evidence decides which screenshot follows which when filenames carry no step number. Second, the modelling decision that every screenshot intake must make and the packet never states: whether the image is a different screen or the same screen in a different state, and what that means for loading, empty and error. It builds on iteration 1 findings 4 (pixel diff settles screen versus state) and 6 (the before/after pair carries a trigger), and widens the source set with two corpus repos never cited by phase 009 or phase 016: `prasantloki__figjam-builder` and `bluescaban__blueprints`.

## Findings

1. **Order comes from a structure the source carries, and four structures exist; the packet names only the weakest.** A deck of numbered items means sequence: "Numbers say 'sequence' or 'of 25' — use them when order or count is the point", and its rule is to "Number a decision flow; bullet a feature list" [SOURCE: research/corpus/prasantloki__figjam-builder/SKILL.md:34]. The card grammar orders by an explicit numbered step list inside a lane: "Steps in the same lane connect sequentially" [SOURCE: research/corpus/bluescaban__blueprints/docs/specs/card-grammar.md:143], and by explicit edges wherever the author supplied them [SOURCE: research/corpus/bluescaban__blueprints/docs/specs/card-grammar.md:141]. Iteration 1 found a third: the before/after pairing around a trigger [SOURCE: research/corpus/figma__mcp-server-guide/workflow-skills/video-interaction-mapper/SKILL.md:20]. Flow Mode names a fourth only: the trigger grammar inside a filename, with one question when two orders fit [SOURCE: AI Systems/Product Owner/sk-create-figjam/references/flow-mode.md:111]. So a set of screenshots with no filenames and no numbering — the common case — falls straight to the question, when two cheaper signals (pixel-diff adjacency, and the order the user supplied them in) were never read.

2. **A screenshot set can be ordered by adjacency before any filename is parsed.** Iteration 1 established that a pixel diff returns a changed percentage and up to twelve changed-region boxes [SOURCE: .skilled/skills/sk-vision/feature-catalog/pixel-analysis/diff.md:22]. A diff of every adjacent pair in the order supplied gives a chain: a pair that differs by a small region is one screen in two states, and a pair that differs across the viewport is two screens. That produces both the ordering evidence and the screen-versus-state verdict from one pass, and neither the packet's intake nor its check names it. What must stay: the packet's one-question rule when two orders fit [SOURCE: AI Systems/Product Owner/sk-create-figjam/references/flow-mode.md:111], because adjacency cannot resolve a set that arrived shuffled.

3. **The packet's own shape table conflates a screen with an action, and says nothing at all about a state.** The four shapes are Stadium "the flow starts or ends here", Rectangle "a screen or an action", Rhombus "a choice", Circle "a merge dot" [SOURCE: AI Systems/Product Owner/sk-create-figjam/references/types/user-flow.md:42], [SOURCE: AI Systems/Product Owner/sk-create-figjam/references/types/user-flow.md:43]. A screen and an action are the two things a person can be looking at or doing, and the same shape means both, so the intake has no slot in which to record which one it read. A state is absent from the table entirely. The consequence is visible in the alternative: Figma's SwiftUI guidance says to "render one state in the primary frame, model the others as variants or separate frames" for conditional rendering, and to "model the resulting screen state (loaded, empty, loading spinner) as separate variants, not the hooks themselves" [SOURCE: research/corpus/lightspeedwp__.github/plugins/figma/figma-swiftui/references/code-to-design.md:180], [SOURCE: research/corpus/lightspeedwp__.github/plugins/figma/figma-swiftui/references/code-to-design.md:183].

4. **An empty, loading or error view is a state of a screen until a different trigger reaches it, and the trigger is the test.** Two screenshots of one screen differ by their data, not by a move; the SwiftUI rule draws that line with variants rather than frames [SOURCE: research/corpus/lightspeedwp__.github/plugins/figma/figma-swiftui/references/code-to-design.md:183]. Figma's video workflow draws the same line at a finer grain: it lists the visual change that counts, and that list includes "loaded content, selected state, validation state" next to modal, drawer and navigation [SOURCE: research/corpus/figma__mcp-server-guide/workflow-skills/video-interaction-mapper/SKILL.md:99]. So the rule the packet needs is a test, not a convention: a state becomes its own node only when a different action or event reaches it, or when a reader can be trapped in it. Otherwise it belongs in the label of its screen, and the detail goes under `Left out:` — the line the packet already ships [SOURCE: AI Systems/Product Owner/sk-create-figjam/references/flow-mode.md:240]. Flow Mode already has the judgement that keeps this cheap: no two nodes that always travel together, and no node that can be removed without loss [SOURCE: AI Systems/Product Owner/sk-create-figjam/references/quality-rubric.md:39], [SOURCE: AI Systems/Product Owner/sk-create-figjam/references/quality-rubric.md:37].

5. **A complete flow carries an error exit, and a decision's No branch must land somewhere.** The card grammar makes three requirements of every flow: "At least one entry point (`START:`), at least one successful end (`END:`), at least one exit/error path (`EXIT:` or error handling)" [SOURCE: research/corpus/bluescaban__blueprints/docs/specs/card-grammar.md:22]. Its third inference rule requires both branches and states their defaults: "Every `D:` (decision) must have at least TWO outgoing edges", "**Yes branch**: Continues the happy path", "**No branch**: Routes to error handling, alternative path, or exit" [SOURCE: research/corpus/bluescaban__blueprints/docs/specs/card-grammar.md:163], [SOURCE: research/corpus/bluescaban__blueprints/docs/specs/card-grammar.md:165]. Flow Mode requires every node to have a way in and a way out and a stadium never mid-flow [SOURCE: AI Systems/Product Owner/sk-create-figjam/references/types/user-flow.md:57], and caps a decision at one to three labelled exits [SOURCE: AI Systems/Product Owner/sk-create-figjam/references/types/user-flow.md:56], but nothing requires a negative or error path to exist. A happy-path-only flow therefore passes `flow_check.py` today, and the empty and error views a screenshot set actually contains have no rule that asks for them.

6. **An edge has an actor, and the packet's edge carries none.** The card grammar types a step by who performs it: `S:` is a "User-performed action" and `SYS:` a "System/app-performed action (automatic)" [SOURCE: research/corpus/bluescaban__blueprints/docs/specs/card-grammar.md:60], [SOURCE: research/corpus/bluescaban__blueprints/docs/specs/card-grammar.md:61], and its cross-lane rule is the person-act to system-act to person-act chain [SOURCE: research/corpus/bluescaban__blueprints/docs/specs/card-grammar.md:179]. Flow Mode's connector takes "an optional label" and nothing else [SOURCE: AI Systems/Product Owner/sk-create-figjam/references/types/user-flow.md:47]. Without an actor, "what moves between screens" cannot be told apart from "what the system did while nobody acted", which is precisely why a loading or error view gets invented as a screen instead of read as an outcome. It also gives the never-invent rule something to attach to: an automatically reached state is not a missing user action.

7. **Explicit evidence outranks inference, and the grammar states that precedence as a rule.** "When you provide explicit definitions (e.g., `E:` edges), the system uses ONLY those. When omitted, the system infers intelligently based on context" [SOURCE: research/corpus/bluescaban__blueprints/docs/specs/card-grammar.md:26], [SOURCE: research/corpus/bluescaban__blueprints/docs/specs/card-grammar.md:27]. Flow Mode has the seed of this in its conflict gate — "An edge one source states and the other contradicts is a finding, not a connector" [SOURCE: AI Systems/Product Owner/sk-create-figjam/references/quality-rubric.md:61] — but it is stated as a prohibition, not as an order of precedence, and it covers sources contradicting each other rather than a stated edge outranking an inferred one. The ordered ladder this research will rank is: an explicit source edge, then explicit numbering, then lane or container order, then screenshot adjacency, then the trigger grammar, then one question.
