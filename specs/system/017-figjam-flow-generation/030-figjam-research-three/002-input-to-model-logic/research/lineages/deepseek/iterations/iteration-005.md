## Findings

1. **The type is chosen from the reader's question, and the table that says what the type needs is never used as a test.** Section 3 states the rule plainly: "The question the reader needs answered picks the type", and "Ask before drawing when two types fit" [SOURCE: AI Systems/Product Owner/sk-create-figjam/references/flow-mode.md:75]. Four sections later the intake carries a "What each type needs" table whose rows are exactly the evidence a type requires — a user flow needs "the screens in order, the trigger for each move, every choice and its outcomes", a state diagram "the states, the event behind each move and any guard" [SOURCE: AI Systems/Product Owner/sk-create-figjam/references/flow-mode.md:134], [SOURCE: AI Systems/Product Owner/sk-create-figjam/references/flow-mode.md:138]. Nothing connects the two: a request answered by a state diagram, supplied with a screenshot set that shows no events, passes straight to intake and the events are then invented or dropped. The needs table already exists, so the change is to make it a gate rather than a note.

2. **Chunking exists only on the output side, so the first diagram is drawn before anything decides how the input divides.** The packet's budget rules are all about the diagram: "A budget per type ... Over budget, split rather than shrink" [SOURCE: AI Systems/Product Owner/sk-create-figjam/references/flow-mode.md:162], and the cuts run in a fixed order before an overview and detail split [SOURCE: AI Systems/Product Owner/sk-create-figjam/references/flow-mode.md:170]. The matching fidelity requirement is that "Every source step lands in one of the diagrams or is listed as left out" [SOURCE: AI Systems/Product Owner/sk-create-figjam/assets/flow-templates.md:91]. Those two rules point in opposite directions when the input is large: the split is decided from the model, and the ledger is checked against the sources afterwards. Deciding the chunk plan from the ordered source list first makes the ledger checkable and turns the split into an allocation rather than a correction.

3. **The pre-write check protects the model-to-board contract and reads no source at all.** `flow_check.py` states its own scope: "A board is slow to fix once it exists ... Worse, the generator silently drops much of what Mermaid can say, so a model can promise a reader something the board never shows" [SOURCE: AI Systems/Product Owner/sk-create-figjam/scripts/flow_check.py:8], [SOURCE: AI Systems/Product Owner/sk-create-figjam/scripts/flow_check.py:10]. It "parses text only and never renders or runs anything in a label" [SOURCE: AI Systems/Product Owner/sk-create-figjam/scripts/flow_check.py:26]. Every rule it enforces is a property of the model — shape, id, label length, connector direction, lane membership, repeated labels [SOURCE: AI Systems/Product Owner/sk-create-figjam/scripts/figjam_checks/flowchart.py:215]. So the provenance table and the `Left out:` list are claims nothing verifies, and the check's own words name the unverified contract: a model can promise a reader something the board never shows, and equally a model can promise a reader something the source never said.

4. **The one place a source re-read pays is the rows where a mistake is silent.** Reading every source twice to verify the model would defeat the budget and the token cost that the intake already worries about [SOURCE: AI Systems/Product Owner/sk-create-figjam/references/flow-mode.md:116]. But a row whose class is `current behavior` and whose evidence is a quoted line is already the cheapest kind to trust, while a row whose edge is inferred, or whose class is approved direction, proposal or unknown, is exactly the row a reader cannot check for themselves. Bounding the re-read to those rows — one narrow reread per row, with the reason recorded — is the shape the `@deep-research` read-budget rule already uses for its own evidence [SOURCE: .skilled/agents/deep-research.md:42]. That keeps the pass inside the existing one-question intake instead of adding a second round of questions.

5. **The ordered procedure this lineage supports, assembled from its own findings.** Each clause names the iteration that produced it, so the synthesis can rank by evidence rather than by preference: read the Figma reaction graph first where the input is a design file (iteration 4 finding 1); order the remaining items by the precedence ladder, explicit edge then numbering then container then adjacency then filename grammar then one question (iteration 2 finding 7, deepened by iteration 4 finding 3); record every item as a node or an edge with source, class and confidence (iteration 1 findings 5 and 6, iteration 3 finding 4); classify a state against its screen by the trigger that reaches it (iteration 2 finding 4); read acceptance criteria as Given/When/Then triples and a Then with no When as a gap (iteration 3 findings 1 and 2); give a contradicted or contradicted-in-part edge a surface the reply already has (iteration 3 finding 5); test the chosen type against the needs row before modelling (finding 1 above); allocate chunks from the source list before drawing (finding 2 above); and re-read only the unverifiable rows before the gate (finding 4 above). Every clause is a change to how the input is read, and none of them touches the write path, the read-back or the reply.

6. **What the packet already does better than every corpus source, and what the change must not remove.** The model-to-board contract is stronger than anything found in 22 repositories: a fail-closed pre-write check [SOURCE: AI Systems/Product Owner/sk-create-figjam/scripts/flow_check.py:12], a read-back compared with the model rather than with memory [SOURCE: AI Systems/Product Owner/sk-create-figjam/references/flow-mode.md:217], a rollback that deletes only what this write created [SOURCE: AI Systems/Product Owner/sk-create-figjam/references/flow-mode.md:195], and a fidelity ledger that names what the board does not hold [SOURCE: AI Systems/Product Owner/sk-create-figjam/assets/flow-templates.md:119]. The corpus's own screenshot-reading workflow has no checker and no expected model; it verifies by looking at its output [SOURCE: research/corpus/figma__mcp-server-guide/workflow-skills/video-interaction-mapper/SKILL.md:265]. The input side is the thin half, and the entire ranked list this lineage will propose lives there: a record per item, a class per edge, a stated inference order, and one source re-read before the gate.
