# Iteration 004 — How several diagrams share one board, and where the packet's own facts need correcting

Lineage: `deepseek`. Builds on: iteration 001 finding 7 (a multi-diagram board has no composition rule), iteration 002 findings 3 and 8 (no zoning option, no title contract), and iteration 003 findings 1, 2, 3 and 4 (board reading order, board spacing bands, the board entry point, and sections nesting by design). This iteration widens the source set again — public FigJam guidance, Mermaid's own documentation on what a model can steer, and two published diagram-design papers — and it resolves a factual conflict inside the packet rather than working around it.

## Focus

How should a board holding several diagrams be composed — titles, sections, legends, reading order and spacing between diagrams — so a reader meets it in the intended order?

## Findings

1. **The packet's page claim is half wrong, and correcting the reason matters more than the correction.** `flow-mode.md` states "A FigJam file has one page and no write can add another, so a page is never the target." Figma's own documentation says the opposite about the file: "FigJam files can contain multiple pages, giving you more space to explore... There is no limit to the amount of pages you can create in FigJam", and lists exactly the reasons a board would want them — separate work streams, recurring meetings, divider pages, and reducing board size and load time. The second half of the packet's sentence is true and is the part that governs behaviour: no *write* can add a page, because `figma.createPage()` throws in a FigJam file. The rule survives; the sentence should be reworded to say that a tool cannot add a page while a person can, because that difference is what lets a multi-diagram board grow past one canvas when the reader needs it. [SOURCE: AI Systems/Product Owner/sk-create-figjam/references/flow-mode.md:65] [SOURCE: https://help.figma.com/hc/en-us/articles/24005082123159-Create-and-manage-pages-in-FigJam] [SOURCE: research/corpus/lightspeedwp__.github/plugins/figma/figma-generate-diagram/SKILL.md:59]

2. **A FigJam section can be created *around* objects that already exist, so the packet can group a generated diagram without moving a single node.** Figma documents "Create section from selection": select and drag the objects, right-click, "Create section". Sections exist to "Cluster objects together without having to group them" and to "Contain objects that can be moved together around the board". The packet's prohibition — "A section never wraps a generated node, because adding a node to a section moves it" — is protecting against `appendChild`, which is the wrong affordance for a diagram that already exists. Wrapping from selection gives the grouping with no coordinate change, so the prohibition can be narrowed to the append path rather than the whole idea. [SOURCE: https://help.figma.com/hc/en-us/articles/4939765379351-Organize-your-FigJam-board-with-sections] [SOURCE: AI Systems/Product Owner/sk-create-figjam/references/hybrid-workflow.md:148]

3. **Sections bring four board-level capabilities the packet uses none of, and each one maps to a quality the scorecard already scores.** Figma lists: cluster without grouping, contain as a movable unit, "Hide sections of the board that can be revealed when needed", "Link collaborators to a specific section of the board", and "Set as thumbnail". The first is grouping (Layout), the second is what makes a diagram feel like one object rather than a cluster of loose nodes, the third is how a board can hold an appendix without competing (Clarity), the fourth is how a reply can point a reader at the right part of a six-diagram board (Reply), and the fifth decides what a reader sees first in the file browser — the board's own first glance. [SOURCE: https://help.figma.com/hc/en-us/articles/4939765379351-Organize-your-FigJam-board-with-sections]

4. **Section titles are first-class objects, and the packet's floating title node competes with them.** Figma's help documents "Edit section title", a toolbar control and a double-click path, plus a way to remove a title when "the section has no title text inside it". Figma's own board skill draws the matching conclusion and clears the name — "**Clear all section names** unless the section has no title text inside it" — so on a FigJam board there are exactly two title mechanisms and the rule is to pick one per region. The packet has neither: it writes a 64px-clear charcoal text node only when an extension was asked for, and never names the diagram in a way the board's own navigation can show. [SOURCE: https://help.figma.com/hc/en-us/articles/4939765379351-Organize-your-FigJam-board-with-sections] [SOURCE: research/corpus/lightspeedwp__.github/plugins/figma/figma-use-figjam/references/plan-board-content.md:106] [SOURCE: AI Systems/Product Owner/sk-create-figjam/references/hybrid-workflow.md:150]

5. **Locking is the missing safety mechanism that would let a diagram be generated inside its own section.** Figma's section lock offers "**Lock all** to prevent the section and its contents from being moved or edited" and "**Lock background only** to prevent the section from being moved or deleted while its content is still editable". The packet refuses sections because `appendChild` moves the node; a locked section background is exactly the state in which that move cannot happen quietly. This is recorded as a route to verify rather than a ruled fact, because no source states what the hosted generator does when the target region is locked, and the packet's own rule forbids claiming an unobserved generator behaviour. [SOURCE: https://help.figma.com/hc/en-us/articles/4939765379351-Organize-your-FigJam-board-with-sections] [SOURCE: research/corpus/lightspeedwp__.github/plugins/figma/figma-use-figjam/references/position-figjam-nodes.md:85]

6. **Multi-diagram composition already has a published shape: one outer section, one zone section per diagram, on Figma's own gaps.** Figma's board skill says "Always wrap the entire board in one top-level white section" and "Sections nest. A board is a section that contains zone sections, which contain card sections", with `siblingGapH: 92` and `siblingGapV: 120` between sibling sections and 68/60/100/80 padding inside one. Applying that to a multi-diagram board is a direct mapping: one board wrapper, one zone section per diagram, each zone named with the diagram's title, 92px between zones in a row and 120px between rows. The packet currently has no spacing figure at all between two diagrams. [SOURCE: research/corpus/lightspeedwp__.github/plugins/figma/figma-use-figjam/references/plan-board-content.md:92] [SOURCE: research/corpus/lightspeedwp__.github/plugins/figma/figma-use-figjam/references/plan-board-content.md:117]

7. **The board should be able to carry a numbered reading order, because every source describes one and none describes a way to signal it.** Figma's board skill fixes the direction ("left-to-right, top-to-bottom", context then evidence then asks then appendix); the composition grammar fixes the glance order (first, second, last); a published architecture-diagramming deck states the goal as "Easy to read: our audience should be able to understand our diagram in seconds" and "Standalone: major parts must make sense without additional explanation". A six-diagram board currently gives a reader no signal about which diagram is first. A section title with an ordinal in it — "1 · Booking states" — is the cheapest available form, and it costs nothing the packet forbids. [SOURCE: research/corpus/lightspeedwp__.github/plugins/figma/figma-use-figjam/references/plan-board-content.md:38] [SOURCE: https://www.lasssim.com/wp-content/uploads/2022/06/WeAreDevelopers_Lasselsberger_Simon_220610.pdf] [SOURCE: research/corpus/prasantloki__figjam-builder/references/composition-grammar.md:5]

8. **"Reshape the model" needs a lever table, because most Mermaid layout hints do nothing and one of them does the opposite of what a reader expects.** Mermaid's own layout note is blunt: "None of these *place* a node, they are requests that the renderer may override", and "The `&` syntax looks as if it might group nodes or put them on the same rank. It does not." The levers that do something are narrower than the packet assumes: extra dashes extend an edge by at least a rank but are "not implemented in ELK"; invisible links move nodes but with an "unpredictable effect"; a subgraph constrains its contents but adds a box that has to be hidden; **subgraph declaration order reverses the rendered order of sibling subgraphs**; and node declaration order "has a bearing on the order in which they are included… but is then often overridden… to try to prevent lines from crossing". [SOURCE: https://line9.ai/mermaid/layout]

9. **Because the FigJam generator is ELK-based, the one length hint the packet could have used is unavailable, which leaves exactly three model-side levers.** The packet's own type reference says a user flow is "laid out by the generator's ELK engine", and Mermaid's note says the extra-dash length hint is "Stock Mermaid — dagre only — not implemented in ELK". What survives on ELK is: direction (already used), node declaration order (unused, and subordinate to crossing minimisation), and the edge set plus subgraph presence (used for lanes only). "Reshape the model" should therefore be written as those three levers with their limits, rather than as a general invitation to try syntax. [SOURCE: AI Systems/Product Owner/sk-create-figjam/references/types/user-flow.md:38] [SOURCE: https://line9.ai/mermaid/layout]

10. **The lane-order reversal is a concrete defect risk the packet's read-back would not catch as a meaning error.** If sibling subgraphs render "in the reverse of the declaration order", a process whose lanes are declared in the order the work happens can land with its lanes in the opposite order — and the packet's read-back counts lanes and checks that each step sits in one, never that the lanes are in the order the reader needs. A board can therefore pass read-back while reading right-to-left through a process. [SOURCE: https://line9.ai/mermaid/layout] [SOURCE: AI Systems/Product Owner/sk-create-figjam/references/types/process.md:72]

11. **A published design source separates micro from macro whitespace, which names the two spacing systems a board needs at once.** The Dell EMC design-diagramming material defines whitespace as "the part of the diagram left unused", splits it into macro and micro, and calls the balance between positive and negative space "essential to create a functional and esthetic diagram"; micro whitespace is "small pieces of space between shapes, lines, titles, icons". That is the missing vocabulary for this lineage's central spacing problem: iteration 003's 60-92 / 200-400 / 1000+ bands are macro whitespace, and the node gap the packet cannot measure is micro. A board needs both, and they are decided in different layers. [SOURCE: https://learning.dell.com/content/dam/dell-emc/documents/en-us/2015KS_Pantyukhin-Principles_of_Design_Diagramming.pdf]

12. **Public accessibility guidance adds the one remedy the packet's tint recipe omits: pair colour with line style, not only with a label.** IBM's technical-diagram guidance says connectors "can also use different colors. However, to avoid color blindness accessibility issues, it's best to use color in combination with labels or line styles so that any difference can be accessible to all users." The packet's style guide already refuses to let colour carry meaning alone, which is a genuine strength, but its tint recipe encodes group membership with fill and stroke only and gives no line-style channel. The cheap repair is available and already inside the palette record: the stroke dash patterns the comparator uses for optional and security nodes. [SOURCE: https://www.ibm.com/design/language/infographics/technical-diagrams/design/] [SOURCE: AI Systems/Product Owner/sk-create-figjam/references/style-guide.md:33] [SOURCE: .skilled/skills/sk-design/sk-design-diagram/references/foundations/style-guide.md:143]

13. **Crossings can be judged before the board exists, because they are a property of the graph rather than of the renderer.** A published layout skill classifies the graph first and names "nearly planar topology where crossing count dominates readability" as one of its classes, then picks a renderer from the class. The packet generates first and judges crossings afterwards, from a screenshot, at a cost of a wasted write. Its existing pre-write script is the natural home for a planarity hint: count the edge set, flag the pairs that must cross, and split or re-rank before the gate rather than after the board exists. [SOURCE: https://github.com/openai/plugins/blob/main/plugins/build-web-data-visualization/skills/node-link-and-diagram-layout/SKILL.md] [SOURCE: AI Systems/Product Owner/sk-create-figjam/references/flow-mode.md:68]

## Questions Answered

- "How should a board holding several diagrams be composed — titles, sections, legends, reading order and spacing between diagrams — so a reader meets it in the intended order?" — answered. One outer board section; one zone section per diagram, named with an ordinal and the diagram's title; 92px between zones in a row and 120px between rows, with the 68/60/100/80 inner padding; sections created by wrapping the finished diagram rather than by appending nodes into them, and locked once settled; one reading direction across the board (context, evidence, asks, appendix); a legend group per zone when the zone uses more than two shapes; and the section link in the reply so a reader is handed their entry point. The packet's page rule holds for tools but needs its reason corrected.

## Ruled Out This Iteration

- **Asking the generator to lay out a whole multi-diagram board in one call.** The tool draws one diagram per call and a FigJam file's page cannot be created by a plugin, so composition has to happen in the section layer around the calls.
- **Using `&` or invisible links as grouping syntax.** Mermaid's own documentation states `&` does not group and invisible links are unpredictable; proposing them would fail the packet's own "never invent" rule.
- **Treating the packet's one-page sentence as correct and building on it.** The rule stays, the reason is corrected (finding 1); a later change should not repeat the wrong reason.
