# Iteration 001 — Who decides each board quality in sk-create-figjam today

Lineage: `deepseek` (fan-out). Session `fanout-deepseek-1792563734045-6evjmk`. Builds on: nothing earlier; this is the baseline inventory that later iterations deepen.

## Focus

Which board qualities does `sk-create-figjam` decide today, and for each one, does `generate_diagram` own it, can the Mermaid model steer it, or does a `use_figma` extension add it afterwards? The question matters because every "the board reads worse than it should" claim later in this lineage is only actionable if it names the layer that can change the outcome.

2. Read the colour, judgment and extension layers: `references/style-guide.md`, `references/quality-rubric.md`, `references/hybrid-workflow.md`.

## Findings

1. **The packet already carries an explicit three-layer ownership model, and that model is a genuine strength worth protecting.** `flow-mode.md` names the generator as layout owner ("The generator owns the layout. Never move a generated node or rewire its connectors"), the model as the means by which a bad layout is fixed ("a layout that reads badly is fixed by splitting the diagram or reshaping the model, not by dragging"), and `hybrid-workflow.md` as the additive layer ("Every addition is a new node beside or behind the diagram"). Any improvement must land in one of those three layers, not invent a fourth. [SOURCE: AI Systems/Product Owner/sk-create-figjam/references/flow-mode.md:164] [SOURCE: AI Systems/Product Owner/sk-create-figjam/references/hybrid-workflow.md:17]

2. **Layout direction is the only geometric lever the Mermaid model actually owns, and each type pins it differently.** A user flow runs `flowchart TD` or `flowchart LR` and is laid out by the generator's ELK engine; a process "runs `TD` or `LR`" with "one direction for every process diagram in the file"; an architecture is "`flowchart LR` only" through a separate grid layout that "errors or silently mis-draws when its rules are broken"; a state diagram is `stateDiagram-v2` running "`LR` or `TB`"; a gantt chart's axis unit is "picked from the chart's length" by the generator. So direction is steerable for four types, fixed for architecture, and unavailable for gantt. [SOURCE: AI Systems/Product Owner/sk-create-figjam/references/types/user-flow.md:38] [SOURCE: AI Systems/Product Owner/sk-create-figjam/references/types/process.md:44] [SOURCE: AI Systems/Product Owner/sk-create-figjam/references/types/process.md:75] [SOURCE: AI Systems/Product Owner/sk-create-figjam/references/types/architecture.md:78] [SOURCE: AI Systems/Product Owner/sk-create-figjam/references/types/state.md:60] [SOURCE: AI Systems/Product Owner/sk-create-figjam/references/types/gantt.md:16]

3. **Spacing has no rule in the model layer at all; every number in the packet belongs to the extension layer.** The only measurements stated anywhere are extension clearances: a sticky sits "40 pixels clear" of its node, a section resizes to its stickies "plus 32 pixels on every side", a title is "64 pixels clear of its top edge", the legend column starts at the widest existing node plus 250 pixels and stacks at a 32-pixel gap, and a tint rectangle is "24 pixels larger on every side". The gap between two generated nodes is never specified, because the packet treats it as generator property. That is the single largest unowned surface in the packet: node spacing, rank spacing and edge clearance are the qualities a reader calls "cramped" or "airy", and no layer here is asked to think about them. [SOURCE: AI Systems/Product Owner/sk-create-figjam/references/hybrid-workflow.md:114] [SOURCE: AI Systems/Product Owner/sk-create-figjam/references/hybrid-workflow.md:148] [SOURCE: AI Systems/Product Owner/sk-create-figjam/references/hybrid-workflow.md:150] [SOURCE: AI Systems/Product Owner/sk-create-figjam/references/hybrid-workflow.md:101] [SOURCE: AI Systems/Product Owner/sk-create-figjam/references/hybrid-workflow.md:118]

4. **Titles exist only as an optional extension, and the generator's own title field is left undefined.** The packet says "A title is a text node above the diagram, 64 pixels clear of its top edge, in charcoal `#1E1E1E`, naming what the reader is looking at" — inside the extension recipe, gated like any other addition, and only reached when the gate named an extension. Meanwhile the write call sets `name` "to a distinct title that matches its hand-off", and nothing in the packet says whether that name renders on the board or lives only in the file's layer list. A reader arriving at a board with no extension gets no title, and a multi-diagram board gets no headings above its parts. [SOURCE: AI Systems/Product Owner/sk-create-figjam/references/hybrid-workflow.md:150] [SOURCE: AI Systems/Product Owner/sk-create-figjam/references/flow-mode.md:186]

5. **Grouping is type-gated rather than a design decision, and one clause removes the board's own grouping primitive.** Sections are explicitly barred from holding generated content — "A section never wraps a generated node, because adding a node to a section moves it" — so on a generated diagram, grouping survives only as an architecture lane, a process lane (`subgraph` with 2–6 lanes, never nested) or a gantt section. A user flow is forbidden any subgraph at all. The consequence is that the one on-board grouping affordance a reader recognises instantly, the FigJam section, is available only for legend stickies. [SOURCE: AI Systems/Product Owner/sk-create-figjam/references/hybrid-workflow.md:148] [SOURCE: AI Systems/Product Owner/sk-create-figjam/references/types/process.md:58] [SOURCE: AI Systems/Product Owner/sk-create-figjam/references/types/process.md:72] [SOURCE: AI Systems/Product Owner/sk-create-figjam/references/types/user-flow.md:55] [SOURCE: AI Systems/Product Owner/sk-create-figjam/references/types/architecture.md:42]

6. **Density is measured as a node count only, so a diagram can pass its budget and still be unreadable.** The budgets are node- and item-shaped: at most 9 nodes and one accent for a user flow, sk-design-diagram's general 9 nodes and 12 connectors, at most 12 gantt tasks with sections once there are more than 8 and at most 5 parallel bars in a section. Nothing measures the relationship between content and area — connector-to-node ratio, labels per unit area, longest path depth, or the number of connectors that must cross the diagram to reach their target. Two models of 9 nodes can produce a calm board and an unreadable one. [SOURCE: AI Systems/Product Owner/sk-create-figjam/references/types/user-flow.md:64] [SOURCE: AI Systems/Product Owner/sk-create-figjam/references/flow-mode.md:162] [SOURCE: AI Systems/Product Owner/sk-create-figjam/references/types/gantt.md:67]

7. **A multi-diagram board has no composition rule: later diagrams reuse the `fileKey` and nothing says where they land or how they read in sequence.** The packet's multi-diagram thinking is entirely about identity and rollback — "Every later diagram of the same work and every revision passes that file's `fileKey`, so the work stays on one board", and the tag is keyed by the diagram's name "because a later session can rebuild it". There is no rule for the gap between diagrams, for a shared heading band, for a numbered reading order, or for which diagram a reader should meet first. FigJam itself has sections and a page, both of which are usable, but the packet's section clause (finding 5) closes the obvious route. [SOURCE: AI Systems/Product Owner/sk-create-figjam/references/flow-mode.md:187] [SOURCE: AI Systems/Product Owner/sk-create-figjam/references/flow-mode.md:190] [SOURCE: AI Systems/Product Owner/sk-create-figjam/references/hybrid-workflow.md:148]

8. **Colour roles are deliberate and well-recorded, but two of the seven types are effectively colourless and the reason is structural.** An architecture "takes no colour from the model", because its layout "assigns shapes and colours by lane" and "the check refuses styling there". Sequence, state and ER lose Mermaid styling altogether, so their colour arrives only as a status tint behind a group. The style guide is honest about what did not translate — "Fonts and the type ramp", "The 4px grid, node sizes and connector routing", "The bottom legend strip" — and it explains each omission. That candour is a strength; what is missing is a replacement rule for the hierarchy work those omitted tokens used to do. [SOURCE: AI Systems/Product Owner/sk-create-figjam/references/style-guide.md:48] [SOURCE: AI Systems/Product Owner/sk-create-figjam/references/style-guide.md:128] [SOURCE: AI Systems/Product Owner/sk-create-figjam/references/style-guide.md:129] [SOURCE: AI Systems/Product Owner/sk-create-figjam/references/style-guide.md:130]

9. **Text size is explicitly not steerable, and the only text control left is length.** Labels are capped at "at most 40 characters on one line" and gantt task names at 40 with no colon, while font family, size and weight are listed under what did not translate: "The generator sets FigJam's font, and the tool cannot change it afterwards". The one typographic lever the packet does hold is the hybrid title (charcoal `#1E1E1E`) and the 20px digit inside a pin. So a board's type hierarchy is currently one size for every label, and "where the eye lands first" can only be carried by shape count, accent and label length. [SOURCE: AI Systems/Product Owner/sk-create-figjam/references/flow-mode.md:160] [SOURCE: AI Systems/Product Owner/sk-create-figjam/references/style-guide.md:128] [SOURCE: AI Systems/Product Owner/sk-create-figjam/references/hybrid-workflow.md:81]

10. **Read-back verifies existence, direction and label text, and never verifies order, position or adjacency.** The read-back counts nodes, connectors, labels and decision exits, compares each connector's two ends and its end caps, and names a dangling connector a mismatch — all of which is genuinely rigorous for what it covers. It says out loud that "Direction comes from the connector, never from its position on the board", which is exactly the sentence that leaves position unverified: a board whose nodes landed in an order no reader would follow still passes read-back. [SOURCE: AI Systems/Product Owner/sk-create-figjam/references/flow-mode.md:219] [SOURCE: AI Systems/Product Owner/sk-create-figjam/references/flow-mode.md:223] [SOURCE: AI Systems/Product Owner/sk-create-figjam/references/types/user-flow.md:95]

11. **The scorecard finally makes layout scorable, but its Layout dimension is a crossing counter and its Clarity dimension is three questions.** Layout's three bands are "no overlap, no connector crossing and one reading direction that matches the model" (2), "no overlap and one crossing" (1), and "any overlap, or two or more crossings" (0). Clarity is a fresh reader answering "the scenario's three questions" from one screenshot. Nothing scores whitespace, grouping, sectioning, title presence, edge-label placement, or whether the board has a beginning. The passing bar is 12 of 14 with Fidelity, Hygiene and Reply at 2, so a board can fail nothing that is specifically about how it reads. [SOURCE: AI Systems/Product Owner/sk-create-figjam/manual-testing-playbook/manual-testing-playbook.md:81] [SOURCE: AI Systems/Product Owner/sk-create-figjam/manual-testing-playbook/manual-testing-playbook.md:83] [SOURCE: AI Systems/Product Owner/sk-create-figjam/manual-testing-playbook/manual-testing-playbook.md:87]

12. **The packet is already strong where most diagram skills are weak: it refuses to invent, refuses to restyle, and writes down why a feature is absent.** "A diagram of a real, partial system beats a polished one of an imagined system", the two dials (detail level, audience) are set before modelling, a fourth decision exit is split into two decisions rather than squeezed in, and the style guide records a measured departure table with the numbers behind each refusal. These are the parts of the packet that make it trustworthy, and none of the changes this lineage will rank touches them. ## Questions Answered

- "Which board qualities does sk-create-figjam decide today, and for each one, does generate_diagram own it, can the Mermaid model steer it, or does a use_figma extension add it afterwards?" — answered. The ownership map is: direction and grouping vocabulary via the model (findings 2, 5); all geometry, spacing, font and node size via `generate_diagram` (findings 3, 9); colour by type, and every annotation, title, section, tint and sticky via `use_figma` (findings 3, 4, 8). Verification covers existence and text but not order or position (finding 10).

## Ruled Out This Iteration

- **Treating the 4px grid as recoverable.** It is a `sk-design-diagram` token for a renderer this packet does not own; `style-guide.md` records it as a deliberate omission, and re-proposing it would only re-add a rule nothing can enforce. Direction for later iterations: replace the grid's hierarchy role rather than the grid.
- **Re-proposing "the generator owns layout, never move a node."** This is already the packet's strongest guardrail and matches the implemented change set from the earlier `017` research. Recorded as a strength, not a gap (finding 12).
