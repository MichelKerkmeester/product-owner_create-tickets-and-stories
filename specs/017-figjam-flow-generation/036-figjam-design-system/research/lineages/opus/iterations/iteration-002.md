## Findings

1. The palette has three hand-kept copies and the composer's JavaScript source is the authority the self-test parses: the self-test reads shape pairs and kind pairs out of `compose-board.js` text with two regexes [SOURCE: AI Systems/Product Owner/sk-create-figjam/scripts/compose_board.py:700-701], the Mermaid check keeps its own `ACCENT_PAIRS` [SOURCE: AI Systems/Product Owner/sk-create-figjam/scripts/figjam_checks/common.py:47-57], and the style guide keeps the table between `FIGJAM_PALETTE` markers [SOURCE: AI Systems/Product Owner/sk-create-figjam/references/style-guide.md:107-120]. A design spec file that adds a fourth copy without becoming the one source would make drift worse, so the spec must replace the composer's literals, and the self-test regexes must read the spec, not the JS.
2. The self-test's accent check covers kinds only, never tints, which is why iteration 1's pink zone tint ships green: `accent_palette_checks` collects strokes from `SHAPE` and pairs from `KINDS` and tests that only the focus kind draws light pink [SOURCE: AI Systems/Product Owner/sk-create-figjam/scripts/compose_board.py:712-727], while `TINT_CYCLE` is never inspected [SOURCE: AI Systems/Product Owner/sk-create-figjam/assets/compose-board.js:48]. The playbook even writes pink into the graders' allowed tint cycle [SOURCE: AI Systems/Product Owner/sk-create-figjam/manual-testing-playbook/manual-testing-playbook.md:97], so neither the code check nor the human scorecard can catch it. Deepens iteration 1 finding 1.
3. The types disagree in their own docs about what a zone colour means. The architecture reference says the composer "colours it by that lane" [SOURCE: AI Systems/Product Owner/sk-create-figjam/references/types/architecture.md:16], while the code colours architecture parts by kind and only the lane chooses the kind [SOURCE: AI Systems/Product Owner/sk-create-figjam/assets/compose-board.js:64-68]; the process reference says each lane gets its own tint, "pale enough that a lane reads as a container" [SOURCE: AI Systems/Product Owner/sk-create-figjam/references/types/process.md:97]; and the check describes a lane as taking "one neutral tint" [SOURCE: AI Systems/Product Owner/sk-create-figjam/scripts/figjam_checks/common.py:59-61]. Three wordings for one element is a consistency defect in the docs that a single `zones` token block would settle.
4. A zone can already carry its own tint, but nothing ever sets it: the composer uses `z.tint || TINT_CYCLE[...]` [SOURCE: AI Systems/Product Owner/sk-create-figjam/assets/compose-board.js:593] and the model builder never writes `tint` (no occurrence in `compose_board.py` beyond the docstring [SOURCE: AI Systems/Product Owner/sk-create-figjam/scripts/compose_board.py:9]). This dormant hook is the natural place for a spec-driven tint rule, such as "tint a zone from a hue no kind inside it uses", which would fix iteration 1 finding 3 without a new model field.
5. The type references describe each board's colours in prose, type by type, rather than pointing to one table: user flow [SOURCE: AI Systems/Product Owner/sk-create-figjam/references/types/user-flow.md:49], state [SOURCE: AI Systems/Product Owner/sk-create-figjam/references/types/state.md:54], gantt [SOURCE: AI Systems/Product Owner/sk-create-figjam/references/types/gantt.md:53], sequence [SOURCE: AI Systems/Product Owner/sk-create-figjam/references/types/sequence.md:54], architecture [SOURCE: AI Systems/Product Owner/sk-create-figjam/references/types/architecture.md:53]. Each restates hex-level choices already in the style guide's kind table [SOURCE: AI Systems/Product Owner/sk-create-figjam/references/style-guide.md:44-79]. A restyle would have to edit eight files plus their Project mirrors; the types should say "colour by kind, see the design spec" and keep only their role mapping.
6. The design surface already has a firm "no skins" ruling: "Skins and brand onboarding still stay behind. A board is shared and recoloured in FigJam, so a brand palette would turn every swatch into a custom colour" [SOURCE: AI Systems/Product Owner/sk-create-figjam/references/style-guide.md:206], and a font or colour change is a hand edit in FigJam [SOURCE: AI Systems/Product Owner/sk-create-figjam/manual-testing-playbook/boundaries/restyle-is-a-hand-edit.md:19]. A user-editable spec must respect the reason behind it: colours should be chosen by FigJam swatch name (lightBlue, lightGreen ...) rather than arbitrary hex by default, and an arbitrary hex should be an explicit opt-in that the check reports as off-palette. That keeps the board recolourable and still lets a user remap meaning to taste.
7. Code room is the hard constraint on how the composer reads a spec. One `use_figma` call takes 50,000 characters and a run past it fails [SOURCE: AI Systems/Product Owner/sk-create-figjam/references/flow-mode.md:347], and the compact template already leaves under 6,400 characters for the model JSON [SOURCE: AI Systems/Product Owner/SYNC.md:100]. A full token file pasted into every call would eat a large share of that, so the composer should receive only a compact, resolved override object (a `__THEME__` placeholder filled by `compose_board.py` beside `__MODEL__` [SOURCE: AI Systems/Product Owner/sk-create-figjam/scripts/compose_board.py:569-571]), and the defaults stay in the JS.
8. The claude.ai Project cannot run the script or read a local file: its Board Composer Knowledge file holds the compact code byte-for-byte with `compose_board.py --template`, and the self-test fails on drift [SOURCE: AI Systems/Product Owner/SYNC.md:92], while a Project "cannot read a local file" [SOURCE: AI Systems/Product Owner/SYNC.md:82]. So the Project reads a spec only if it ships as a Knowledge file and the agent fills `__THEME__` by hand from it, exactly as it fills `__MODEL__` today. The byte-equality gate stays intact because the placeholder, not the theme, lives in the mirrored code.
9. The 22-point scorecard has no criterion for cross-type consistency or for conformance to a declared style: its overview dimensions are composition, crossings, shared trunks and label collisions, and its reading dimensions fidelity, legibility, signal and clarity [SOURCE: AI Systems/Product Owner/sk-create-figjam/manual-testing-playbook/manual-testing-playbook.md:81-93]; the rubric's eight design criteria score one board at a time [SOURCE: AI Systems/Product Owner/sk-create-figjam/references/quality-rubric.md:126-139]. Nothing scores "this board looks like a sibling of the others" or "this board matches the active design spec", so iteration 1's cross-type drift (key order, line language, light blue meanings) is invisible to grading.
10. Positive, keep: the self-test already measures what a spec's safety floor needs. It computes WCAG contrast [SOURCE: AI Systems/Product Owner/sk-create-figjam/scripts/figjam_checks/common.py:157-158], checks the accent's hue distance of at least 45 degrees from every kind and its 3:1 mark gate on white [SOURCE: AI Systems/Product Owner/sk-create-figjam/scripts/compose_board.py:702-727], and re-measures every palette row [SOURCE: AI Systems/Product Owner/sk-create-figjam/references/style-guide.md:105]. Pointing those same checks at a resolved user theme is the validation layer, with no new measuring code.

## Ruled out

- Letting the model carry per-node colour again: the packet deliberately reads a `style` line as meaning, not paint [SOURCE: AI Systems/Product Owner/sk-create-figjam/references/style-guide.md:122-133]. A design spec restyles kinds globally; it must not reopen per-node paint.
