# Iteration 002 — Style Reference contract and cross-runtime safety

## Focus

Design the packet-level Style Reference contract, safe token schema, cross-runtime handoff, mirror parity, and scorecard conformance path.

## Builds on

Iteration 2 builds on Iteration 1 findings 1, 2, 4, and 5: preserve the common visual grammar, separate type semantics from shared tokens, clarify score scope, and eliminate duplicated design authority.

## Actions Taken

- Read the sk-design Style Reference generator, its authoring boundary and validation assets, the Product Owner Project parity note, the packet templates and examples, and the composer/Python integration points.
- Compared public DESIGN.md examples and the Design Tokens Community Group format report.
- Reconciled the quality rubric and playbook totals against their stated scoring dimensions.

## Findings

1. Correction to Iteration 1: the score totals describe different scopes rather than contradictory math. quality-rubric.md Section 7 scores eight overview-design criteria out of 16; the playbook’s 22-point whole-board score uses four overview measures, four reading-zoom measures, four invariants, and the reply. Keep both views but state their relationship explicitly; the gallery has nine entries, so eight screenshots besides sequence-board.png score 21–22/22. 2. Put the editable reference at packet scope: AI Systems/Product Owner/sk-create-figjam/DESIGN.md is specific to the composer that draws these boards and gives the repository user one visible place to restyle all seven types. Do not place the override at repository root or duplicate an editable copy there. Treat it as a forward-authored FigJam design contract, not as an output from sk-design-md-generator, whose Style Reference workflow measures existing web CSS and explicitly excludes brief-only authoring. [SOURCE: AI Systems/Product Owner/sk-create-figjam/references/style-guide.md:18-22,26-28; .skilled/skills/sk-design/sk-design-md-generator/SKILL.md:12-14,42-46]
3. Use a human-readable Style Reference with one strict, versioned JSON token block as its machine contract. Public DESIGN.md examples present a portable agent-facing guide and can identify a canonical source; the Design Tokens Community Group format supplies a useful typed JSON pattern with grouped values and descriptions, while its report is not a W3C Standard. Borrow that structure as a bounded subset rather than parsing arbitrary prose or claiming the packet file is an extracted site reference. [SOURCE: https://github.com/stella/stella/blob/main/DESIGN.md:190-194; https://github.com/dimabraven/design-md:203-232; https://www.w3.org/community/reports/design-tokens/CG-FINAL-format-20251028/:27-35,298-312,402-424]
4. Define shared and type-specific tokens without changing what colors mean. The shared schema should cover paired fills/strokes/text by semantic kind; font family, weight and scale for title, subtitle, zone/key, node, edge, field and source; grid and spacing; shape stroke and supported rounding; connector line, dash, weight and arrow caps; zone tints; key/title/source surfaces; and the first-glance accent. Add per-type token groups for sequence request/reply/async arrows and pins, state start/final/choice, architecture lanes, ER relationships, gantt status/milestone, and flow/process lanes or branches, while keeping role names and one accent invariant.
