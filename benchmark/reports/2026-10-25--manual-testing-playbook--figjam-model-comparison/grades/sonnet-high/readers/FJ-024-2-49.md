# Fresh reader: FJ-024-2-49

## 1 Title and the question this board answers

The title is "Block sync". The subtitle reads "The parts that carry a block change from a Loomlist client to the others, for Loomlist engineers". So the board answers: which components does a block change pass through on its way from one client to the other clients?

## 2 What you see first, and what second

First I see the sync-service node, because of its thick pink outline in the middle of the board. Second I see the row of tinted group panels from left to right (Clients, Edge, Services, Events, Stores and External) and then the Key strip along the bottom.

## 3 The main path or structure from start to end, naming the shapes

This is an architecture or component diagram read left to right.

- Clients panel: three teal rounded rectangles stacked vertically, Desktop App, Web App and iOS App.
- Each client links to the API Gateway (blue rounded rectangle in the Edge panel) with a solid line labelled "Live socket". Each of these has an arrowhead at both ends.
- API Gateway goes to sync-service (white rounded rectangle with pink outline, Services panel) by a solid one-way arrow labelled "Routes sync requests".
- sync-service goes up and over to Blocks Database (purple cylinder, Stores panel) by a solid one-way arrow labelled "Writes block changes".
- sync-service goes to Change Stream (orange horizontal cylinder, Events panel) by a dashed arrow labelled "Publishes changes".
- Change Stream goes down and back left to Push Worker (white rounded rectangle, lower in the Services panel) by a dashed arrow labelled "Feeds".
- Push Worker goes right to Apple Push (grey rounded rectangle, External panel) by a dashed arrow labelled "Apple Push: Wakes iOS device".

A footnote under the key says file storage was left out because no call to it is stated, and that the wake hop from Apple Push to the iOS app is not drawn.

## 4 Relationships, messages or timing

There are no decisions or branches. The relationships are:

- Desktop App, Web App and iOS App each hold a two-way live socket with API Gateway.
- API Gateway routes sync requests to sync-service (synchronous, one way).
- sync-service writes block changes to Blocks Database (synchronous, one way).
- sync-service publishes changes to Change Stream (async).
- Change Stream feeds Push Worker (async).
- Push Worker calls Apple Push to wake the iOS device (async or outside call).

No timing or ordering numbers are shown, so the order of the write and the publish is not stated.

## 5 What the key says, and whether every mark is in the key

The key lists: teal rounded rectangle for app or client, blue rounded rectangle for edge or gateway, white rounded rectangle for service, orange cylinder for queue or stream, purple cylinder for data store, grey rounded rectangle for outside system, dashed arrow for async or outside call, solid double-headed arrow for both ways and a thick pink outline for in focus.

Not every mark is keyed. The solid single-headed arrow (used for "Routes sync requests" and "Writes block changes") has no key entry, so I have to infer it means a synchronous one-way call. The tinted group panels and their colours (pale blue, peach, pale teal, pale yellow) are not in the key either, though their titles explain them. The Change Stream is drawn as a horizontal cylinder while the key swatch is drawn similarly, so that matches.

## 6 Anything I could not read, could not follow or found ambiguous

- The subtitle promises the change reaching "the others", but no line carries a change back out to Desktop App or Web App. Nothing connects Change Stream or sync-service back to API Gateway, so the fan-out to other live clients is missing or only implied by the two-way sockets (centre left of the board).
- The last hop from Apple Push to the iOS App is admitted as not drawn (footnote), so the iOS delivery path ends at the External panel on the right.
- It is unclear whether the iOS app, once woken, fetches the change over its live socket or some other way.
- The label "Apple Push: Wakes iOS device" repeats the target name, which reads a little oddly but is legible.
- The footnote starts with "Source: your request", which is meaningless to a reader who did not write the request.
- The Writes block changes arrow leaves the top of sync-service and runs above the Events panel, which is easy to follow but long.
- All text was readable at 100 percent.

## 7 Could a product manager act on this board without asking anyone?

No, because the board shows how a change gets in and gets stored and how iOS is woken, but it never shows how the change actually reaches the other desktop and web clients, which is the very question the subtitle sets.
